## 1. 测试策略

采用三层门禁，从内到外逐层校验：

```
┌─────────────────────────────────┐
│  L3  UI 巡检（26 项，真实浏览器）  │  人能看到吗？
├─────────────────────────────────┤
│  L2  接口冒烟（36 项，对线上服务） │  接口能用吗？
├─────────────────────────────────┤
│  L1  pytest（116 项）            │  算得对吗？
│      ├─ 55 内核单测（纯函数）      │
│      └─ 61 接口测试（真实 HTTP）   │
└─────────────────────────────────┘
```

**设计意图**：算法逻辑用纯函数单测覆盖（无 IO、毫秒级），接口行为用真实 HTTP 测试（临时库 + 随机端口，不污染开发库），界面用真实浏览器巡检（含移动端与截图）。

## 3. 缺陷记录与修复

测试过程中共发现并修复 14 个缺陷，全部闭环。

| # | 缺陷 | 根因 | 修复 |
|---|---|---|---|
| D1 | 服务启动即崩，`UnicodeEncodeError: latin-1` | `server_version` 用了中文品牌名，HTTP 头只能 latin-1 | 改为 `"FeiHuaAPS/" + VERSION` |
| D2 | `/api/health` 要求登录 | 未加入公开白名单 | 白名单加 `/api/health`、`/api/sync/version` |
| D3 | 执行排程报 `no such column: no` | `schedule_runs` 主键列名是 `run_no` | `gen_no(..., col="run_no")` |
| D4 | 登出后 token 仍可用 | 对 dict 用 `getattr(u, "_token")` 取不到 | 改 `(u or {}).get("_token")` |
| D5 | 同工作中心工序被判重叠 | 日桶模型允许相邻工序同日不同时段衔接 | 校验口径改为"每日负荷 ≤ 日产能" |
| D6 | 逐日负荷累计超产能 | 按工序总时长均摊到跨期，未记录真实占用 | 内核记录 `spans` 每日明细并持久化，服务端直接聚合 |
| D7 | `/api/sync` 恒返回 `{}` | `"".split(",")` 得 `[""]`，误判为"指定了实体" | `[x for x in ... if x]` |
| D8 | 6 处单测断言与内核语义不符 | 断言按直觉写，未对齐实现（如 total_hours 16.5 vs 9.0） | 逐条按内核语义修正断言 |
| D9 | 插单影响面断言失败 | 字符串替换未生效 | 改为直接断言 `"W1" in summary["late_wos"]` |
| D10 | UI 巡检 favicon 404 | 缺图标文件 | 新增 `favicon.svg` 并在两页引用 |
| D11 | 空页巡检失败（主区文字过短） | 页面只有标题 | 补页面说明文字（顺带提升可用性） |
| D12 | 移动端横向溢出 | 表格撑破 | `body { overflow-x: hidden }` + 判定改用 `document.body.scrollWidth` |
| D13 | `pages.js` 语法错误 `missing ) after argument list` | 甘特 title 属性多一个双引号 | 修正字符串拼接 |
| D14 | 控制台 `Cannot read properties of undefined (reading 'catch')` + 3 个 404 | ①`kit`/`master` 页面函数不返回 Promise，`go()` 直接 `.catch` 崩；②首次启动无排程批次，`/api/plan/latest` 与 `/api/plan/load` 返回 404 | ①`go()` 用 `Promise.resolve()` 兜底并 try/catch；②新增 `/api/plan/overview` 空态返回 200，仪表盘改用它；③种子初始化时自动跑首次排程 |

## 5. 性能观测

| 场景 | 数据规模 | 耗时 |
|---|---|---|
| 全量排程 | 10 工单 / 23 工序 / 6 中心 / 90 天视界 | ~120 ms |
| 齐套检查 | 10 工单 / 30 BOM 行 / 12 物料 | ~25 ms |
| CTP 查询 | 10 现有 + 1 模拟工单 | ~130 ms |
| 排程结果读取 | — | ~10 ms |
| pytest 全量 | 116 条 | 4.58 s |
| UI 巡检 | 9 页面 + 6 交互 + 15 截图 | ~75 s |

> 复杂度约为 `O(工单数 × 工序数 × 平均跨天数)`。工单量到数百级时仍在秒级内，可满足车间级使用。若到千级需引入增量重排。

## 6. 已知限制

1. **日粒度**：不做分钟级设备时序仿真，日内冲突交 MES 执行排程处理。
2. **单机部署**：SQLite 单文件，不支持多实例共享同一库（可用只读副本做查询分离）。
3. **CTP 全量重排**：工单数很大时响应时间线性增长。
4. **无自动采购**：只输出缺口，采购动作在 ERP 侧。
5. **工时依赖主数据**：标准工时不准则排程不准，需上线前治理。
